 What the priority number means

  priority: 1  →  most specific / most stable selector (tried first, no warning logged)
  priority: 2  →  fallback — logs: [SelfHealing] Primary selector failed — fell back to 'has-text': button:has-text("Sign In")
  priority: 3  →  last resort — same warning, most fragile (positional/generic selectors)

  If the app is refactored and the button[type="submit"] is renamed, priority 2 (button:has-text("Sign In")) kicks in automatically —
   the test keeps passing and the console warning tells you which selector needs updating.

AIdriventypeAPI.spec 

 It runs 2 API tests whose behaviour is driven by the OpenAPI/Swagger spec (src/openapi.json) rather than hardcoded values. The test
   names, expected HTTP status codes, and endpoint metadata are all read from the spec at runtime.
   
 This is the heart of the AI-driven approach. It reads two things from the spec for any given endpoint:

  ┌──────────────────┬───────────────────────────────────────────────────┬──────────────────────────────────┐
  │ What it extracts │                        How                        │          Example result          │
  ├──────────────────┼───────────────────────────────────────────────────┼──────────────────────────────────┤
  │ summary          │ Reads op.summary from the spec                    │ "Register a new user"            │
  ├──────────────────┼───────────────────────────────────────────────────┼──────────────────────────────────┤
  │ okStatus         │ Finds the first 2xx response code in op.responses │ 201 for register, 200 for events │
  └──────────────────┴───────────────────────────────────────────────────┴──────────────────────────────────┘

  Step by step:
  1. rawSpec.paths['/auth/register']['post'] — goes to that exact endpoint in the spec
  2. op.summary — reads the human-readable description written by the API team
  3. Object.keys(op.responses) — gets all response codes ['201', '400']
  4. .find(s => Number(s) >= 200 && Number(s) < 300) — picks the first success code (201)
